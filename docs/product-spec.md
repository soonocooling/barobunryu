# 바로분류 (가칭)

## 한 줄 소개
결제 직후 애매한 거래만 텔레그램으로 묻고, 대충 쓴 답으로 분류와 엔빵 차감까지 끝내는 대학생용 가계부 봇.

## 사용자와 사용 맥락
- 주 사용자: 간편결제·송금 앱을 주 결제 수단으로 쓰고 엔빵이 잦은 대학생 [추론]
- 사용 시점: 결제 후 수 분 안에 텔레그램 질문에 답한다(1탭 또는 한 줄). 대시보드는 주 1~2회 본다.
- 사용 환경: 스마트폰 텔레그램 + 웹 대시보드 1장
- 규모: 해커톤은 팀원 1인의 데이터로 데모한다. 구조는 1인 1봇 [결정]

## 시스템 구조 [결정]
```
[본인 폰]
  결제 알림 ─┬─ (A) 텔레그램에 붙여넣기 / 직접 입력 "스벅 6500"
             └─ (B) MacroDroid(Android) · 단축어(iOS) → Supabase inbox 테이블 (insert 전용 키)

[GitHub Actions, 5분마다] watch.py
  ① state.json 읽기 (tg_offset)
  ② 텔레그램 getUpdates → 새 입력·답장·버튼 처리
  ③ inbox 미처리분 파싱 → transactions 생성
  ④ 분류: 사용자 규칙 → 가맹점 캐시 → 카카오 로컬 API → 키워드 사전
  ⑤ 신뢰도 낮은 거래와 엔빵 의심 거래 → 텔레그램 질문 (반복 금지)
  ⑥ 입금 ↔ 미정산 엔빵 매칭
  ⑦ state.json 저장 → 커밋

[Vercel] 대시보드·설정 1장 ← Supabase 읽기
```
- 서버가 없으므로 응답 지연은 최대 약 5~15분이다(cron 간격과 실행 지연). 데모는 Actions의 `Run workflow`로 즉시 실행한다.
- 저장소는 공개로 둔다(Actions 무료 분 제한 회피). 그래서 민감 데이터는 전부 Supabase에 두고, 저장소에는 금액·이름이 없는 `state.json`만 둔다.

## 화면 구조
- **텔레그램 봇 (주 인터페이스)**: 거래 입력, 확인 질문, 답장, 묶음 리뷰, `/today` `/month` 명령
- **대시보드 (Vercel, 비밀번호 보호, 1페이지)**: 이번 달 순지출·카테고리 합계 / 받을 돈 / 미분류 목록 / 설정 폼

## 기능 명세

### A. 거래 수집

#### F-01 거래 입력  [명시 + 결정]
**동작**: 본인의 결제·이체·입금 정보가 두 경로로 들어오면 구조화된 거래로 만든다.
**세부 요구사항**:
- 경로 A: 텔레그램 봇에 결제 알림을 붙여넣거나 "스벅 6500", "+10000 박세훈"처럼 직접 입력한다. 숫자 앞에 `+`가 있으면 입금이다.
- 경로 B: 폰 자동화 앱이 알림 원문을 Supabase `inbox`에 POST한다(anon 키, RLS로 insert만 허용).
- `parse_push(raw)`가 반환하는 값: `{ts, amount, direction: out|in, method: card|transfer, counterparty}`. 포맷은 해부 단계에서 수집한 `docs/push-samples.md`의 실제 문구를 기준으로 맞춘다.
- 파싱에 실패하면 텔레그램으로 "못 읽었어: (원문 앞 30자)"를 1회 보낸다. 해당 inbox 행은 `failed`로 표시하고 다시 처리하지 않는다.
- 중복 제거: (금액, 상대, 시각 ±2분)이 같으면 하나로 본다.
- 이체 상대가 사람이면 이름 원문은 저장하지 않는다. `sha256(name + SALT)`를 키로 쓰고, 표시는 사용자가 붙인 별칭(없으면 "상대 #n")으로 한다 [결정. 타인 정보 저장 금지 규칙].
**완료 조건**:
- [ ] 텔레그램에 "스벅 6500"을 보내면 다음 실행 후 거래 1건이 생기고 카페·간식으로 분류된다.
- [ ] 같은 결제가 경로 A와 B로 모두 들어와도 거래는 1건이다.
- [ ] Supabase 어디에도 이체 상대의 실명이 없다.

#### F-02 취소·환불 상계  [추론, v1.1]
같은 상대와 같은 금액의 7일 이내 출금 건을 찾아 상계한다.

### B. 자동 분류

#### F-03 자동 분류  [명시]
**동작**: 거래가 생기면 카테고리와 신뢰도 $c$를 정한다.
**세부 요구사항** (먼저 걸리는 단계에서 멈춘다):
1. 사용자 규칙(`rules`, F-07): $c=0.95$
2. 가맹점 캐시(`merchant_cache`): 저장된 $c$
3. 카카오 로컬 API: `documents[0].category_group_code`가 매핑표에 있으면 $c=0.85$. 문서는 있는데 매핑이 없으면 $c=0.5$. 결과는 캐시에 저장한다.
4. 키워드 사전: $c=0.8$
5. 위에서 모두 실패: `etc`, $c=0.2$
- 이체(`method=transfer`)는 1단계 규칙이 없으면 `transfer`, $c=0.3$으로 둔다. 즉 처음 보는 이체 상대는 반드시 묻는다.
- 내 계좌 간 이체("내 ○○통장" 같은 패턴, `self_accounts` 설정)는 `self`로 두고 집계에서 제외한다.
- $c < \theta$(기본 0.7, 설정 가능)이면 `status=pending`이 되고 F-05 대상이다.
**완료 조건**:
- [ ] 처음 보는 이체 상대에게 송금하면 항상 질문이 온다.
- [ ] 같은 가맹점이 두 번째 나오면 카카오 API를 호출하지 않는다(캐시 적중).

### C. 확인 질문 (핵심 UX)

#### F-05 확인 질문과 답장 처리  [명시]
**동작**: 애매한 거래만 텔레그램으로 묻고, 버튼 1탭이나 한 줄 답장으로 확정한다.
**세부 요구사항**:
- 메시지: `[확인] 10/27 19:42 · 상대 #3 23,000원 출금. 뭐였어?`
- 인라인 버튼: 후보 2개 + `엔빵` + `기타`. `callback_data = "c:{txn_id}:{code}"` (64바이트 이내)
- 답장(해당 메시지에 reply)은 `parse_answer(text)`가 규칙으로 파싱한다 [결정: 해커톤 MVP는 LLM 없이 규칙 파서]:
  - `(\d+)\s*명` → 엔빵 n
  - `내\s*몫\s*([\d,]+)` → 내 몫 금액
  - `카테고리 키워드 사전`(치킨→food, 책→edu, 택시→transport …)에서 첫 번째로 매칭되는 카테고리
  - "몰라", "패스" → etc 확정
  - 아무것도 매칭되지 않으면 카테고리 버튼만 다시 보낸다(1회)
- 확정되면 원래 메시지를 `✅ 식비 · 4명 엔빵 (내 몫 5,750원)`으로 수정한다(editMessageText). 새 메시지는 보내지 않는다.
- 반복 금지: `asked_at`이 있는 거래는 다시 묻지 않는다.
- 하루 질문 상한(기본 5)을 넘거나 23~08시에 들어온 거래는 21시 이후 첫 실행에서 묶음 메시지 1통으로 보낸다(F-06).
- 버튼 응답이 다음 실행에서 처리되므로 answerCallbackQuery는 만료될 수 있다. 오류는 무시한다.
**완료 조건**:
- [ ] 버튼 1탭으로 분류가 확정되고, 원래 메시지가 ✅ 문구로 바뀐다.
- [ ] "치킨 4명" 답장 → 식비, 엔빵 4명으로 기록된다.
- [ ] 다음 실행에서 같은 거래 질문이 다시 오지 않는다.

#### F-06 21시 묶음 리뷰  [결정]
미뤄진 거래를 한 메시지에 번호 목록으로 보낸다. "1 식비 2 치킨 3명"처럼 한 줄 답장으로 일괄 처리하고, 버튼은 거래별로 단다. 처리할 거래가 0건이면 보내지 않는다. `state.json.last_digest_date`로 하루 1회만 보낸다.

#### F-07 교정 학습  [추론]
같은 상대·가맹점을 같은 카테고리로 2회 확정하면 `rules`에 등록한다($c=0.95$). 다른 카테고리로 확정하면 규칙을 해제한다. 대시보드에서 규칙을 삭제할 수 있다.
**완료 조건**:
- [ ] 상대 #3을 '주거·통신'으로 두 번 답하면, 세 번째 이체는 질문 없이 분류된다.

### D. 엔빵

#### F-08 대표결제 엔빵  [명시]
**동작**: 엔빵 n이 지정되면 지출은 $\lceil T/n \rceil$(내 몫)만 잡고, 나머지 $R = T - \text{내 몫}$은 받을 돈으로 둔다.
**세부 요구사항**:
- 트리거: 답장의 "n명", 버튼 `엔빵`(→ "몇 명?" 후속 질문), 엔빵 의심(식비·카페 ≥ 30,000원이면 질문 버튼 첫 자리에 `엔빵`) [결정]
- "내 몫 15000"이 있으면 그 금액을 우선 적용한다.
- 정산 입금은 수입이 아니라 받을 돈 상환으로 처리한다.
**완료 조건**:
- [ ] 46,000원을 4명 엔빵하면 월 지출 +11,500원, 받을 돈 +34,500원이 된다.

#### F-09 정산 입금 매칭  [명시]
**동작**: 입금이 들어오면 미정산 엔빵과 연결한다.
**세부 요구사항**:
- 후보: 생성 후 14일 이내이고 `remaining > 0`인 엔빵 중 입금액이 $|{\rm amt} - T/n| \le 10$원이거나 `≤ remaining`인 것
- 후보가 1개면 자동 매칭하고 사후 알림 1줄을 보낸다. 2개 이상이면 "어느 정산?" 버튼(최대 3개 + `일반 입금`)으로 묻는다.
- 엔빵 지정 없이 3만원 이상 출금한 뒤 24시간 안에 비슷한 금액(±10%) 입금이 2건 이상 오면 "엔빵이었어? (n명 추정)"를 1회 묻는다. 이게 원문의 "정산된 금액을 지출에서 빼기" 경로다.
**완료 조건**:
- [ ] 4명 엔빵 후 11,500원 입금 3건이 들어오면 사용자 조작 없이 받을 돈이 0이 된다.
- [ ] 정산 입금은 월 수입에 잡히지 않는다.

#### F-10 역방향 엔빵 (친구가 대표결제)  [추론]
이체 질문의 답장에 "고기 내 몫"처럼 '내 몫' + 카테고리 키워드가 있으면, 그 이체를 해당 카테고리 지출로 집계한다.
**완료 조건**:
- [ ] "고기 내 몫" 답장 → 해당 이체가 식비로 집계된다.

### E. 가계부·분석

#### F-11 순지출 집계  [명시]
순지출 = 출금 − 계좌 이동(`self`) − 엔빵 타인 몫 − 정산 입금 매칭분. 텔레그램 `/today` `/month`와 대시보드가 같은 계산식(Supabase view `monthly_summary`)을 쓴다.
**완료 조건**:
- [ ] 대시보드와 `/month`의 합계가 같다.

#### F-12 대시보드·설정 화면  [결정, 배포 URL 조건]
Vercel 1페이지. 기본 인증(`DASH_PASSWORD`)으로 보호한다. 구성은 월 합계와 카테고리 막대, 받을 돈 목록, 미분류 목록, 규칙 목록(삭제), 설정 폼(θ, 하루 상한, 묶음 시각)이다.
**완료 조건**:
- [ ] 비밀번호 없이 접속하면 401이 뜬다.
- [ ] 설정에서 θ를 바꾸면 다음 실행부터 반영된다.

#### F-13 월간 패턴 리포트  [명시, v1.1]
카테고리 추이, 고정비 후보(같은 상대·금액 ±5%·간격 28~31일 3회 이상), 3개월 평균 대비 +50% 이상인 카테고리를 매월 1일 텔레그램으로 보낸다.

## 비기능 요구사항
- 프라이버시: 저장소 공개, 데이터는 Supabase에만 둔다. 서비스 키는 Actions Secrets와 Vercel 환경변수에만 둔다. inbox용 anon 키는 RLS로 insert만 허용한다.
- 시간대: 모든 판정은 Asia/Seoul 기준이다. cron은 UTC라는 점에 주의한다.
- 지연: 입력부터 질문까지 cron 간격 + 실행 지연(목표 15분 이내)
- 출처 표시: README와 대시보드 하단에 "장소 분류 데이터: Kakao Local API"

## 범위 밖
- 원본 앱이나 금융기관 API 직접 연동(3등급), 원본 앱 파일 분석
- 실시간 응답(웹훅 서버). 해커톤은 폴링으로 한다.
- 예산, 자산, 투자, 다중 사용자, LLM 자유 입력 파싱(v1.1)

## 확인이 필요한 결정사항
1. **거래 원천**: 본인 알림 텍스트를 본인이 보내는 방식이 조건 ②("데이터는 공개 API에서만")에 해당하지 않는다고 보고, 공개 API는 카카오 로컬로 충족한다. → **멘토 확인 필요**. 불허되면 대안은 데모를 더미 거래 CSV로 하는 것이다.
2. **폴링 구조**: GitHub Actions 5분 cron. 대안인 웹훅 서버는 매뉴얼의 "혼자 도는 코드" 방식에서 벗어나고 세팅 시간이 늘어난다.
3. **저장소 공개 + Supabase**: 비공개 저장소는 5분 cron 기준 월 약 8,600분이 필요해서 무료 2,000분을 넘는다.
4. **자유 입력 파서**: 규칙 기반이 채택안이다. LLM 파싱은 v1.1이고, 키는 Secrets `LLM_API_KEY`로 둔다.
5. **엔빵 회계**: 결제 시점에 내 몫만 지출로 잡고 나머지는 받을 돈(채권)으로 둔다.
